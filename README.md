# WS2812B LED matrix driver — bare-metal Rust on ESP32-C3

Firmware that drives a 16x16 WS2812B LED matrix from an ESP32-C3 with no OS and no runtime beyond a small heap: the frame is composed with zero-copy 2D iterator combinators and emitted bit-exact over the RMT peripheral, with timing derived from the WS2812 datasheet and validated on real hardware.

This project started as a datasheet exercise: take the WS2812B signaling spec, turn it into hardware-timed pulse trains.

## What it does

- **Bit-exact WS2812B signaling.** The datasheet defines four time windows (T0H/T0L ≈ 400/850 ns, T1H/T1L ≈ 800/450 ns, RES > 50 µs). These are converted to pulse counts at the RMT's 80 MHz clock (12.5 ns resolution, computed in picoseconds to avoid truncation) and emitted as single-wire pulse trains on `GPIO0`.
- **Hardware timing, not software timing.** Every bit is generated by the ESP32-C3's RMT peripheral. The idle output is held low so that any gap between transactions resets the chain instead of leaving a stuck LED on — a real-world bug I diagnosed and fixed by reading the peripheral behavior, not the datasheet of the LED.
- **Zero-copy frame composition.** The whole frame (scrolling text, overlapping sprites, serpentine wiring) is one lazily-evaluated iterator pipeline — nothing is copied until the final 256-pixel `Vec`:
  - `GraphicIter3by5` / `GraphicIter5by5` — tiny 3x5 / 5x5 bitmap glyphs stored as bitfields.
  - `Position<I>` — places a glyph at an (x, y) offset.
  - `Composite2dIter` — composites two positioned layers onto one canvas with a overlaps-b priority.
  - `Chain2dIter` — tiles buffers horizontally.
  - `Flip2dIter` — resolves the serpentine (boustrophedon) wiring of physical LED matrices: it walks rows and reverses direction line-by-line using a line-seekable iterator trait, so logical (x, y) maps correctly onto the physical data line without materializing a framebuffer.
- **Measured, not assumed.** Startup logs benchmark frame composition against a plain `Range` iterator baseline (`core::hint::black_box` to defeat dead-code elimination), so the cost of the compositing layer is a number, not a feeling.
- **Allocator usage under `no_std`.** Runs `#![no_std]` / `#![no_main]` with a sized `esp_alloc` heap (72 KB) and `alloc` collections, showing where dynamic allocation is actually needed on an MCU and where it is avoided.

## Why this maps to real embedded work

Driving a WS2812 chain is a bounded-latency problem: the wire protocol has no ACK, no clock line and no error recovery — a mistimed frame is silently wrong. That forces the same discipline as production sensor work:

- interpreting a hardware datasheet's nanosecond-level timing tables and device tolerances;
- choosing the right peripheral (RMT) and configuring clock resolution, divider and idle levels;
- reasoning about CPU clock configuration (`CpuClock::max()`) and its effect on peripheral timing;
- validating achieved timing and throughput on the target, with numbers in the logs;
- handling link-level resets (RES frame) and frame pacing in a `!` (never-returning) main loop.

## Hardware

| Part | Detail |
|---|---|
| MCU | ESP32-C3 (`riscv32imc-unknown-none-elf`, bare metal) |
| Matrix | 16x16 WS2812B |
| Data pin | `GPIO0` |
| Timing peripheral | RMT TX channel @ 80 MHz (12.5 ns pulse resolution) |
| Radio | `esp-wifi` initialized (BLE feature available for future remote control) |

Building & flashing:

```sh
# Nix flake provides the toolchain (stable + rust-src + riscv32imc target) and espflash
direnv allow          # or: nix develop

cargo run --release   # flashes via espflash and opens the monitor
```

CI (GitHub Actions) runs `build --release`, `fmt --check` and `clippy -D warnings` on every push.
